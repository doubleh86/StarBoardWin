# 개발 작업 규칙

## 목적

이 문서는 Starboard for Windows의 구현, 문서, 검증, Git 작업 흐름을 정의한다.
`C:/Work/TRK-Server`의 작업 범위 축소와 plan-first 원칙을 가져오되, 서버·DB
운영 규칙은 포함하지 않는다.

GPT-6 Astra의 자율 진행, 지침 충돌과 검증 범위에 관한
[OpenAI 공식 가이드](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#prompting-best-practices)를
참고했다(2026-09-05 확인). 아래 내용은 이 저장소의 운영 기준이며, 모델 이름만으로
제품 제약이나 검증 수준을 바꾸지 않는다.

## 작업 시작 순서

1. 루트 `AGENTS.md`를 읽는다.
2. Git 저장소라면 branch, worktree, 변경 상태를 확인한다.
3. 현재 작업과 직접 관련된 파일과 문서를 `rg`로 찾고 완료 조건을 정한다.
4. 아래 Plan-first 대상이면 기존 계획을 갱신하거나 새 계획을 작성한다.
5. 요청을 완결하는 가장 작은 변경을 구현하고 해당 검증을 마친다.

전체 코드와 모든 문서를 먼저 읽지 않는다. 이미 확보한 문맥은 재사용하고, 변경
가능성이 있거나 판단에 필요한 부분만 다시 확인한다.

## 지침의 역할과 충돌 처리

- 시스템·개발자 지침과 실행 환경의 권한 제한을 따른다. 그 안에서 사용자의
  명시적인 요청과 기존 승인은 저장소 문서와 스킬의 일반적인 권고보다 우선한다.
- 제품 제약과 module 경계는 `AGENTS.md`, 작업 절차와 검증은 이 문서, C#/XAML은
  `docs/code-style.md`, 계획 양식은 `docs/plans/README.md`를 정본으로 삼는다.
  상세 문서는 루트의 제품 제약을 유지하는 범위에서 구체화한다.
- 지침과 코드가 충돌하면 관련 선언, 호출부와 근거를 확인한다. 요청 범위 안에서
  판단 가능한 차이는 해결하고 기존 계획 또는 완료 보고에 이유를 남긴다.
- 스킬이나 문서 때문에 확인이 필요하거나 작업을 멈추면 정확한 파일 링크와
  해당 문구, 현재 작업에 적용되는 이유를 설명한다. 권고를 임의의 승인 조건으로
  확대하지 않는다.

## 자율 진행과 질문

- 사용자 운영 방침(2026-09-10): 버그 제보와 기능 제안은 기본적으로 관련 기획서에만
  기록한다. 오케스트레이터 작업과 충돌하지 않도록 직접 제품 코드를 수정하거나 작업을
  시작하지 않는다. 사용자가 직접 수정·구현을 명시적으로 요청한 경우에만 구현한다.
  별도로 요청한 빌드·배포·커밋·푸시는 해당 범위에서 수행한다.
- 구현이나 수정을 원하는 요청은 실행 요청으로 처리한다. 분석이나 계획 제시에
  그치지 않고 요청된 변경, 검증과 필요한 문서 갱신까지 완료한다. 사용자가 검토나
  계획만 요청했다면 그 범위에 맞춘다.
- 요청 범위의 되돌릴 수 있는 코드·문서 수정, 조사, 로컬 build/test와 디버깅은
  스스로 진행한다. 기존 코드와 근거로 정할 수 있는 구현 선택은 직접 결정하고
  결과에 영향을 주는 가정만 기록한다.
- 제품 방향·UX 불변 조건이나 호환 정책 변경, 요청 범위 확장, 되돌리기 어려운
  조치, 확보되지 않은 권한·장비가 필요할 때 확인한다. 수정 파일 수나 새로운
  adapter의 필요성만으로 멈추지 않는다.
- 같은 범위에서 이미 받은 승인은 다시 묻지 않는다. 확인이 필요하면 먼저 현재
  요청과 승인으로 해결되는지 살피고, 추가 결정이 필요한 이유를 구체적으로 쓴다.
- 필수 요구사항이 빠졌으면 초기에 묻고 답변에 의존하지 않는 작업을 계속한다.
  실행 승인 전에는 승인 없이 할 수 있는 조사·구현·검증을 마쳐 검토 가능한
  변경과 영향을 준비한다. 응답이 없다는 사실을 승인으로 간주하지 않는다.
- 진행 중 추가 질문에는 짧게 답한 뒤 작업을 이어 간다. 정정·제약은 진행 중인
  작업에 반영하고, 명시적인 취소나 목표 교체가 없으면 원래 완료 조건을 유지한다.

## 변경 범위

- 수정 줄 수가 아니라 요구사항을 완결하는 가장 작은 논리적 범위를 기준으로
  한다.
- 직접 영향받는 declaration, caller, contract, setting, test, documentation은
  함께 확인한다.
- 요청 범위 밖 기능, 미관 개선, 대규모 formatting, dependency 교체, 파일 이동을
  끼워 넣지 않는다.
- 작업과 관계없는 사용자 변경은 유지한다. 다른 변경을 reset, stash, 삭제 또는
  덮어쓰지 않는다.
- 관련 없는 기존 미사용 코드는 발견 사실만 보고한다.

## Plan-first

다음 작업은 제품 코드보다 계획 문서를 먼저 작성하거나 갱신한다.

- 새 사용자 기능
- Win32/ConPTY/WebView2 등 플랫폼 구조 추가 또는 변경
- dependency 추가·교체·제거
- 설정 schema나 저장 위치 변경
- 여러 계층 또는 여러 프로젝트에 걸친 refactor
- 기존 계획의 범위 확장

계획 문서는 `docs/plans/YYYY-MM-DD-topic.md` 형식으로 작성하며
`docs/plans/README.md`의 항목을 따른다. 작업 중 범위가 바뀌면 구현을 계속하기
전에 계획의 범위, 영향 파일, 위험 및 검증 방법을 먼저 갱신한다. 요청 범위 안의
계획 작성·갱신은 승인 대기 단계가 아니다.

위 대상에 해당하지 않는 문서 수정, 국소적인 버그 수정, 상태 확인, 이미 계획된
작업의 작은 후속 수정, build/test 실행은 별도 계획 없이 진행할 수 있다. 필요한
검증과 판단 근거는 기존 계획 또는 완료 보고에 남긴다.

## 구조 전환 판단

다음 상황에서는 기존 구조 유지와 새 구현의 범위, 호환 부담, 위험 및 검증 비용을
비교하고 계획에 선택과 근거를 기록한다.

- 현재 구조를 유지하기 위한 compatibility 코드가 새 구현보다 커지는 경우
- 둘 이상의 외부 계약 또는 renderer/platform boundary를 함께 바꿔야 하는 경우
- 기존 구조 수정 비용이 새 adapter 또는 V2 구현보다 클 것으로 예상되는 경우
- 제품 UX 원칙과 기술적 제약이 직접 충돌하는 경우

제품 제약과 요청 범위를 지키는 구현 선택은 에이전트가 결정해 계속 진행한다.
위의 질문 기준에 해당할 때만 추천안, 대안과 실제 영향을 정리해 확인한다.

## 구현 흐름

- 각 phase가 끝날 때 solution을 build 가능한 상태로 유지한다.
- 먼저 pure logic과 interface boundary를 만들고, 실제 native integration은 얇게
  연결한다.
- 실패 시 같은 명령이나 같은 수정을 반복하지 말고 원인을 좁힌다.
- dependency를 추가하기 전에 platform 제공 기능과 이미 선택된 dependency로
  해결 가능한지 확인한다.
- runtime network가 필요한 dependency 또는 CDN asset은 사용하지 않는다.
- architecture와 실제 구현이 달라지면 같은 작업에서 문서를 갱신한다.

## 병렬 작업

- 서로 독립적인 검색과 조회는 묶어서 실행하고 결과를 모두 확인한다. 앞선 결과에
  의존하는 작업, 파일 수정과 build/test처럼 같은 산출물을 쓰는 작업은 순서대로
  진행한다.
- 하위 에이전트는 사용자 또는 적용 중인 지침이 명시적으로 위임을 요청한 경우에
  사용한다. 독립적인 목표, 파일 소유 범위와 완료 조건을 정할 수 있는 작업만
  나누고, 주 에이전트가 결과 통합과 최종 검증을 책임진다.

## 검증

변경의 실제 영향으로 검증 범위를 정한다. 다음 표에서 해당하는 기준을 적용하고,
여러 유형이 섞이면 필요한 검증을 함께 수행한다.

| 변경 유형 | 필요한 검증 |
| --- | --- |
| 문서만 변경 | `git diff --check`, 변경 내용의 사실·규칙 정합성, 링크 확인. 제품 동작과 빌드 입력에 영향이 없으면 .NET 명령 생략 |
| 제품 코드 변경 | 관련 test 또는 project부터 검증하고 완료 전 solution restore/build와 전체 automated test 수행 |
| dependency, project reference, 빌드 설정·스크립트, renderer asset 변경 | solution restore/build/test와 해당 architecture·asset·배포 경로 검증 |
| phase 종료 또는 release | solution 전체 검증과 해당 integration/manual matrix 확인. 미수행 항목은 pending으로 기록하고 release 완료 조건과 구분 |

제품 변경을 완료할 때의 기본 명령은 다음과 같다.

```powershell
dotnet restore Starboard.Windows.sln
dotnet build Starboard.Windows.sln --configuration Debug --no-restore
dotnet test Starboard.Windows.sln --configuration Debug --no-build --no-restore
```

`--no-restore`와 `--no-build`는 현재 변경과 같은 configuration의 선행 단계가
성공했을 때만 사용한다. 같은 변경에 필요한 검증이 이미 통과했다면 완료 보고를
위해 다시 실행하지 않는다. 이후 변경, 실패 또는 해소되지 않은 위험이 있을 때만
영향받는 검증을 추가하거나 반복한다. 실패한 명령은 원인을 확인한 뒤 재시도한다.

기능과 버그 수정은 기존 테스트가 변경 동작과 회귀 위험을 충분히 검증하는지 먼저
확인한다. 부족한 동작·경계 조건에만 테스트를 추가한다. 되돌릴 수 있는 낮은 영향의
변경에 구현을 그대로 재현하는 테스트를 만들지 않는다.

구현 요청에는 로컬 restore/build/test와 관련 디버깅이 포함된다. 관리자 권한,
설치, 외부 서비스 쓰기, 시스템 설정 또는 파괴적인 데이터 변경이 필요한 검증은
기존 승인과 실행 권한을 확인하고, 부족한 경우 그 작업만 보류한다. 나머지 검증은
계속 진행한다.

검증 보고는 다음을 구분한다.

- 자동 테스트 통과
- 로컬 integration 검증 통과
- simulation 또는 mock으로만 확인
- 실제 hardware/display 환경에서 수동 확인 필요
- 환경 제약으로 미수행

실제로 수행하지 않은 멀티모니터, DPI, fullscreen, IME 검증을 완료로 보고하지
않는다.

## Git과 worktree

- 현재 디렉터리가 Git 저장소인지 먼저 확인한다. 저장소가 아니라면 branch나
  commit이 있다고 가정하지 않는다.
- 동시에 여러 write 작업을 수행하게 되면 작업별 branch/worktree와 파일
  ownership을 분리한다. 겹치는 파일을 동시에 수정하지 않는다.
- 다른 작업자의 dirty change를 이동, reset, stash, 삭제하지 않는다.
- 사용자가 요청하지 않으면 branch 생성, commit, push, merge를 자동으로 하지
  않는다.
- commit을 요청받으면 서로 관계없는 변경을 한 commit에 섞지 않는다.
- TRK 형식을 적용하는 commit message는 다음을 사용한다.

```text
[클라이언트, 실제 작성자] - 작업 내용
[문서, 실제 작성자] - 작업 내용
```

- 작성자에는 `AI`, `Codex` 같은 도구명을 사용하지 않는다. 실제 작성자 이름을
  알 수 없으면 첫 commit 전에 확인한다.
- commit 전에 `git diff --check`와 변경 파일 목록을 확인한다.

## 생성물과 로컬 파일

다음 파일은 source로 관리하지 않는다.

- `bin/`, `obj/`, `out/`, `artifacts/`, `TestResults/`
- `.vs/`, `.idea/`, 개인 `.vscode/` 설정
- `*.user`, `*.suo`, `*.log`
- WebView2 user data와 crash dump
- 로컬 shell path override와 machine-specific settings
- secret, token, credential, private environment file

bundled xterm.js처럼 제품이 runtime에 필요로 하는 검토된 정적 asset은 생성물이
아니며 source 또는 재현 가능한 dependency restore 대상으로 관리한다.

## 완료 보고

한국어로 결과를 먼저 쓰고 변경 이유와 근거를 짧게 연결한다. 다음 중 실제로
해당하는 내용만 포함한다.

- 변경한 동작과 필요한 파일 링크
- 실행한 검증과 결과, 생략한 검증이 있다면 이유
- 남은 제약이나 사용자 결정이 필요한 구체적인 항목

긴 도구 실행 기록, 계획의 반복, 모든 작업에 같은 제목·체크리스트를 붙이는
보고는 피한다. 진행 중에는 새로 확인한 사실과 다음 판단에 필요한 내용을 알린다.
