계획과 검증 범위를 명확히 하고 문서 사이의 충돌을 해소한다.

## 현재 상태

- `AGENTS.md`는 사소한 선택의 자율 처리를 요구하지만 workflow에는 구조 변경 시
  일괄적으로 멈추고 사용자에게 선택지를 보고하는 규칙이 있다.
- 계획 대상과 전체 검증의 적용 범위가 문서마다 달라 작은 변경에 과도한 절차를
  적용할 여지가 있다.
- 빈 `catch` 허용 여부와 interop 배치 경로가 루트 지침과 코드 스타일에서 다르다.
- 기존 작업의 v0.1 계획 수정, orchestrator roadmap과 `.ai-orchestrator/`가 있다.
  이번 변경 대상과 분리해 보존한다.

## 구현 범위

- 실행 요청, 기존 승인, 중간 요구 변경과 실제 확인이 필요한 상황의 처리 기준
- 저장소 문서와 스킬의 역할, 충돌 처리와 중단 사유의 설명
- 계획 작성 대상과 기록 분량, 독립 조회와 위임의 조건
- 문서 변경과 제품 변경을 구분한 검증 기준, 불필요한 재검증의 종료 조건
- 코드 스타일의 interop 경로, 오류 처리와 테스트 지침 정합성

## 제외 범위

제품 코드, C# 표기 취향, 제품 UX와 module 경계, 의존성, 모델 설정, 기존 작업의
계획과 orchestrator 설정, commit과 push는 변경하지 않는다.

제품 아키텍처 변경은 없다. 루트 지침은 제품 제약과 실행 원칙, workflow는 작업

## 위험 영역과 fallback

- 자율 진행을 요청 범위 확장이나 권한 우회로 해석하지 않도록 확인 경계를 둔다.
- 검증 간소화가 제품 변경의 전체 automated suite를 생략하게 하지 않는다.
- 문서 검토 결과와 Astra의 실제 장기 작업 성능 검증을 구분한다.

## 완료 요약

구조 변경이나 계획 작성 자체를 승인 조건으로 삼던 문구를 정리했다. 자율 진행,
문서·스킬 충돌 처리, 중간 요구 반영, 위임 조건과 간결한 보고 기준을 명시했다.
계획은 기본 항목과 필요한 추가 항목으로 나눴으며, 문서 변경과 제품 변경의
검증 기준 및 재검증 종료 조건을 맞췄다.

문서 검증을 통과했다. 제품 코드와 빌드 입력을 수정하지 않아 .NET restore,
build, test와 hardware/manual 시나리오는 실행하지 않았다. 제품 UX·아키텍처와
C# 표기 규칙, 기존 계획 및 orchestrator 변경은 보존했다. 추가 조정이 필요하면
`docs/development-workflow.md`의 질문·계획·검증 기준부터 확인한다.
